# 项目想法重构：让已确认的项目规则自动参与 Agent 执行

> 状态：已实现首个最小闭环；后续产品能力仍待评估。
> 范围：产品需求、已落地的最小行为和后续决策。不把后续候选项视为已实现功能。

## 1. 一句话定位

用户确认一次规则后，在相同适用条件下，Agent 不需要用户重复提醒，就能在相关动作发生前获取并遵循规则；PiDeck 让用户知道规则是否真正影响了本次执行。

重点不是“在 PiDeck 加一个知识库浏览器”，而是打通“保存的知识 → 本次适用的规则 → 实际执行 → 可核查结果”。

## 2. 为什么重新构建

上一版列出了很多接入问题，但没有突出三个关键区别：

- **能搜索，不代表会主动搜索。** 工具可用不等于每次任务都会使用。
- **读过，不代表遵守。** 全文进入上下文后，Agent 仍可能遗漏条件、错误理解或在后续步骤中忘记。
- **声称采用，不代表有执行证据。** 一条“已加载”提示不能证明上传确实走了指定代理。

上一版还把“上传时使用 7890”缩窄成“连接失败后才使用”。本次恢复原意：用户希望在适用的上传动作开始时就遵循规则。是否仅失败后使用，必须由规则本身或用户确认决定，不能擅自补充。

## 3. 核心用户故事：上传 Release 不再重复提醒

用户已经记录并确认一条规则：在约定的项目与环境中，上传 GitHub Release 使用 7890 端口对应的代理。

下一次用户只说：“构建最新 release 并上传到 GitHub。”

期望体验：

1. Agent 识别这次任务包含 GitHub Release 上传，而不要求提示词中出现“代理”或“7890”。
2. 在上传前找到并加载相关规则，判断项目、运行环境、触发条件是否符合。
3. 条件符合且上传已获授权时，按规则执行，不先直连失败再想起代理。
4. 如果代理不可用、规则含义不完整或存在冲突，说明受影响的动作，不静默改走直连。
5. 结束时能够说明采用的规则及依据；无法验证实际网络路径时，明确“已配置但未验证”，不冒充遵循成功。

### 例子中的边界

- “7890”只是端口信息，不足以确定代理协议、地址、运行位置或工具是否支持代理。
- 本机规则不自动适用于远程机器；不同机器上的同一端口不代表同一服务。
- 规则可以约束已授权的上传，但不授予发布、覆盖 Release 或推送代码的权限。
- 规则作用于上传，不意味着构建、所有网络请求和所有项目都必须使用该代理。
- 本想法不是要求现在配置代理或上传任何内容。

## 4. 产品问题应拆成五个可诊断环节

| 环节 | 用户需要得到的结果 | 不能混淆的情况 |
| --- | --- | --- |
| 可用性 | 知道本项目的知识来源是否可用 | 检索失败不是“没有相关规则” |
| 发现 | 当前任务能找到适用候选，不依赖用户重复关键词 | 搜索结果不是完整规则 |
| 加载与判断 | 获得正文、来源和条件，解释为何适用或不适用 | 已加载不是已采用 |
| 动作约束 | 适用规则在相关动作前影响行为 | 已采用不是已执行 |
| 结果核查 | 有依据说明遵循情况，或承认无法验证 | Agent 自述不是独立证据 |

自动遵循的可靠性取决于整个链路，而不是单独提高搜索命中率。

## 5. 知识不应全部变成命令

建议在产品讨论中区分以下语义；这不是要求新增数据字段，也不是声称 pi-maestro-flow 已有同名分类。

| 内容性质 | 对执行的合理影响 | 例子 |
| --- | --- | --- |
| 背景事实 | 帮助理解，不直接触发操作 | 项目使用 Electron |
| 经验与建议 | 条件符合时参考，不能擅自升级为强制规则 | 某次下载超时通过代理解决 |
| 已确认约束 | 在明确范围内约束相关动作 | 指定环境上传 Release 必须使用约定代理 |
| 操作授权 | 由用户及现有审批机制决定 | 本次允许发布到 GitHub |

关键区别：历史经验不能仅因为进入知识库就成为永久约束；约束也不能替代操作授权。

规则能否可靠应用，需要理解其来源、有效状态、作用范围、触发条件、要求与例外。若现有知识无法表达清楚，应暴露歧义，而不是由 PiDeck 默默补齐。

## 6. 建议评估的遵循闭环

以下是候选产品方向，不是已经确定的触发实现或界面。

### 6.1 任务开始：确认知识可用性与候选规则

识别当前项目和运行环境，明确知识来源是否可用，发现任务相关规则。没有初始化、工具不可用、访问失败和检索成功但无命中，应有不同含义。

不建议把整库无差别塞进每个任务：无关内容增加干扰，也可能把其他项目或环境的约束错误带入。

### 6.2 相关动作前：形成明确的适用判断

当任务从“讨论发布”进入“实际上传”时，检查与该动作有关的条件是否满足。任务起点没有提到上传，但后续新增了上传动作时，也应有机会补充相关规则。

需要能够回答：采用哪条规则、为什么适用、将如何影响动作、哪些部分仍需确认。是否用提醒、确认或强制门禁实现，暂不确定。

### 6.3 执行与恢复：不能依赖一次阅读永久有效

续聊、上下文压缩、会话恢复或任务委派后，相关规则不能被默认视为仍然完整可用。产品应评估规则在这些边界上的延续与重新确认，但不能把另一任务或旧运行的应用状态当成本次证据。

规则或环境变化后，需要重新判断受影响的动作；不要求无变化时每一步重新搜索。

### 6.4 收尾：按证据反馈，不只显示“已应用”

建议区分以下概念，具体展示方式待定：

- 已发现：只有候选结果。
- 已加载：相关正文已提供给 Agent。
- 拟采用：Agent 判断规则适用，尚未完成动作。
- 有遵循证据：实际动作的相关证据支持该判断。
- 未验证：证据不足，不能断言遵循成功。
- 未采用或受阻：说明条件不满足、冲突、不可用等原因。

以代理为例，命令配置了代理、工具接受了配置、流量实际经过代理，是不同强度的证据。上传成功本身不能证明使用了指定代理。反馈不应暴露凭据或为了证明遵循而收集不必要的敏感信息。

## 7. PiDeck 与 pi-maestro-flow 的责任边界

### 7.1 已有架构约束

根据根目录 [AGENTS.md](../AGENTS.md)：

- pi 负责 Agent 行为、工具执行及会话读写；PiDeck 不替它实现另一套 Agent。
- PiDeck 承担桌面管理和呈现，通过既有 stdio JSON-RPC 与 pi 通信，不引入访问 pi 内部的第二条通信通道。
- 相关状态应保持 session-first，不把一次会话的规则结果混入其他会话。

因此，不能把“PiDeck 自动遵循”理解为 Electron 主进程解析所有命令、替 Agent 改写工具调用并宣称规则已生效。

### 7.2 建议的产品分工，具体协议待评估

| 主体 | 建议职责 |
| --- | --- |
| pi-maestro-flow | 保持知识及治理语义的权威，提供可用的检索、加载与使用信息 |
| pi 运行时及其扩展协作 | 让相关知识参与 Agent 的决策和动作；是否具备规则检查能力需另行确认 |
| PiDeck | 呈现来源可用性、应用证据、异常和用户确认；不维护另一份规则真相 |
| 用户 | 确认规则适用范围、处理需人工决定的冲突、授权高风险动作 |

现有 Plan 适配提供了可参考的责任边界：

- [maestroControls.ts](../src/shared/maestroControls.ts) 将桌面控制转换为上游命令。
- [pi-deck-maestro-auto-approve.ts](../resources/extensions/pi-deck-maestro-auto-approve.ts) 适配 RPC 确认呈现，Plan 状态仍由上游维护。
- [AgentMessageProjector.ts](../src/main/pi/AgentMessageProjector.ts) 区分内部交接内容与用户消息呈现。

这些只是已检查的 Plan 协作例子，**不证明现有知识库已有可直接复用的事件、接口或强制门禁**。直接读取知识文件还是通过受支持的能力访问，仍须调查上游后决定。

本次在当前仓库运行知识检索，因缺少 `.workflow` 目录失败。它只能说明当前检索入口不可用，不能证明用户没有知识库，也不能作为自动初始化知识库的授权。

## 8. 首批候选范围：只验证一条完整链路

建议以“已确认的 Release 上传代理规则”为首批场景，而不是先建设全功能知识管理界面。该选择尚待确认。

候选范围：

- 一个明确的项目、运行环境和已有知识来源。
- 一条含义完整、用户已确认的上传规则。
- 用户不重复规则时，仍能在上传前发现并采用。
- 不可用、冲突和无法验证时，能如实反馈。
- 不改写知识，不扩大上传权限，不影响无关任务。

暂不纳入首批候选范围：多知识源聚合、自动学习并升级为约束、全局规则编辑器、所有工具的通用强制拦截、跨机器规则自动迁移。

## 9. 候选场景验收：验证行为，不只验证搜索

下表供后续产品评估使用，不表示功能已经实现或验证通过。

| 场景 | 期望结果 |
| --- | --- |
| 用户只说构建并上传 Release，规则要求上传走7890 | 上传前采用规则，无需重复提示或等待直连失败 |
| 用户只要求分析发布方案 | 可参考规则，但不能发起上传 |
| 只构建不上传，规则范围仅为上传 | 不把代理要求扩散到全部构建操作 |
| 知识里只是一次失败重试经验 | 不自动升级为“以后所有上传必须代理” |
| 规则明确要求代理，但代理不可用 | 不静默直连；报告受影响动作；是否阻断由后续确认的策略决定 |
| 知识来源无法访问 | 报告未完成知识检查，不声称“无规则”或“已遵循” |
| 两条规则对上传路径要求冲突 | 暴露冲突，不凭更新时间或模型偏好擅自裁决 |
| 任务移到远程环境 | 不直接套用本机7890配置 |
| 压缩或恢复后继续上传 | 重新确保相关规则可用，不沿用未经核查的旧状态 |
| 只有代理配置证据，无实际路径证据 | 明确验证范围，不以成功上传冒充网络路径已核实 |
| 用户授权上传，但知识要求覆盖旧 Release | 规则不扩大授权，不自动执行覆盖 |

候选衡量方式：在固定场景集中记录无需重复提醒的遵循比例、误用到无关动作的比例，以及未遵循时原因能否被定位。不预设尚无依据的数值目标。

## 10. 已确认需求、建议与待决事项

### 已表达的需求

- 减少用户重复告知已记录规则的负担。
- 探索 PiDeck 与 pi-maestro-flow 项目知识库协作。
- 让规则在相关任务中被发现、加载并遵循。
- 考虑应用反馈、遗漏和冲突，同时保留用户控制权。

### 本次已实现的最小闭环

- PiDeck 内置扩展在每轮 Agent 请求前触发知识检查。
- 扩展只在当前 Agent 项目根目录存在 `.workflow` 时查询；不同项目必须使用各自的知识库，不向祖先目录或外部工作区回退，也不创建或复制知识库。
- 查询词从任务提示和项目目录名提取，做长度限制、路径/令牌脱敏；分别搜索 `spec` 与 `knowhow`，最多加载 4 条相关内容。
- 加载内容以受边界约束的项目上下文追加到当前 system prompt；不会覆盖系统/开发者消息，不授予发布、上传、删除或其他高风险操作权限。
- PiDeck 时间线显示“已应用、无命中、候选无法加载、知识库未配置或知识检查不可用”等状态；知识不可用不等同于没有规则。
- 当前实现只做发现、加载和上下文注入，不拦截工具调用，也不宣称已有独立执行证据。

### 本稿提出的建议，尚未批准为实现范围

- 将“可验证的遵循”而不是“知识浏览/加载次数”作为产品中心。
- 先验证一个项目与环境中的上传规则闭环。
- 按证据区分发现、加载、采用与实际遵循。
- 在关键动作与上下文变化边界关注规则，不持续全库注入。

### 进入产品设计前需决定的事项

| 决策 | 需要明确的问题 |
| --- | --- |
| 承诺强度 | 首期只做自动发现与提醒，还是对少量明确规则提供动作前检查？不能把前者宣传为强制遵循 |
| 规则归属 | 7890规则属于哪个项目、哪台环境，代理完整含义及适用动作是什么？ |
| 上游能力 | pi-maestro-flow 能提供哪些稳定的加载、状态和证据能力？缺失部分归谁负责？ |
| 失败策略 | 已知强制规则无法满足、知识入口不可用时，分别提醒、确认还是阻断哪些动作？ |
| 冲突权限 | 用户能临时覆盖哪些规则，哪些上层安全约束不能覆盖？ |
| 可见性 | 需要反馈到什么程度才足以确认遵循，又不造成每轮提示噪声？ |

这些决策尚未确认，因此本稿不选择接入协议、匹配算法、优先级公式、UI 控件或拦截实现。

## 11. 当前实现的限制与下一步

当前最小闭环仍有明确限制：

- “已应用”表示相关知识已搜索并加载进本轮上下文，不表示规则已经被工具动作实际执行。
- 规则冲突、动作前强制检查、代理是否真正承载网络流量，尚未由 PiDeck 独立验证。
- 当前项目必须已经有自己的 `.workflow`；PiDeck 不会把其他项目的 `.workflow`、全局目录或外部工作区当作当前项目知识库，也不会静默初始化知识库。
- `maestro` CLI 不可用、查询失败或加载失败时只报告不可用，不将失败误报为空结果。
- 当前不自动记录 `consumed/validated` 等知识归因，不修改知识库内容。

后续若继续扩展，应优先验证 Release 上传代理规则：确认规则的项目/环境归属、动作前遵循策略、冲突与失败处理，以及什么证据足以说明“实际遵循”。

## 12. 本轮交付标准

- 问题不再停留于“Agent 没搜知识”，而是可定位遵循链路中的缺口。
- 保留原始7890使用意图，不擅自添加失败后重试条件。
- 明确 PiDeck 的适配价值和不替 pi 实现行为的边界。
- 给出主流程与负向场景，避免把成功搜索作为成功遵循。
- 分开原始需求、候选建议和未决产品决策。
- 已实现最小发现/加载/上下文注入闭环，并保留后续动作级遵循的边界。
